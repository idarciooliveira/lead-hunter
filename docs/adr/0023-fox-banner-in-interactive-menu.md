# 0023. Show a pixel fox banner when the interactive menu starts

- Date: 2026-09-29
- Status: Superseded by [0024](0024-shaded-fox-banner.md)
- Amends: [0022](0022-interactive-menu.md)

## Context

The interactive menu opens with a plain text prompt. Competition tools such as Codex and Claude Code greet the user in the terminal with recognizable art. A small tamagotchi-style pixel animal gives the menu a friendly identity at near-zero cost.

Anything shown in the menu must survive the existing contract from ADR 0022: every pixel of the menu is read by tests through `Prompter`'s writer, and piped runs must never get ANSI escape codes or mangled output.

## Decision

- The menu prints a pixel-art fox banner once, before the first prompt, and never again in the loop.
- The art is a 24 by 18 character grid stored as its 12-pixel left half and mirrored at class init in `LeadFox`, so the fox cannot go lopsided. Each letter is one pixel: `.` background, `O` fox orange, `o` light orange, `W` white, `C` cream for the inner ears, `B` brown outline, `K` near-black for eyes, nose and mouth.
- The banner has exactly two render modes:
  - ANSI color, when stdout is a terminal, using 256-color escape codes; a happy face frame may swap in later as a second static frame, with no threads or timers.
  - Plain monochrome, no escape codes, when stdout is not a terminal (pipes, logs, tests).
- No new dependency. Escape codes are generated by hand with `\u001B`, and color is decided with a single check influenced by `NO_COLOR` in the spirit of no-color.org.
- The banner goes through `prompter.out()`, so tests capture it like any other menu output.

## Consequences

Dark terminals without truecolor still render the fox correctly because we stay on the standard 256-color palette. Every terminal renders the plain mode cleanly, so logs and captured output stay coherent. Tweaking the art is editing one string array plus its palette map. If the art needs animation later, that is a new decision.
